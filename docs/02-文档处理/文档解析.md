# 文档解析

主要文件：

- `backend/src/backend/parser.py`
- `backend/src/backend/domain.py`

## 模块定位

文档解析模块负责把整份 PDF 转换成带页码、文本块、表格、图片位置、版面信息和 Markdown 的结构化结果（Document Understanding），是整条 RAG 链路的质量地基。

## 解析管线选型对比

系统支持五条解析管线，通过 `RAG_DOCUMENT_PIPELINE` 切换。选型对比如下：

| 管线 | 模型/引擎 | 能力 | 速度 | 资源 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| `paddlevl`（默认） | PaddleOCR-VL 视觉语言模型 | 版面+表格+公式+OCR 一体，复杂版式还原好 | 慢（GPU 推理，分钟级/百页） | GPU 服务（compose 独立部署，8080 端口） | 扫描件、复杂表格、图文混排规范 |
| `pdf-extract-kit` | OpenDataLab PDF-Extract-Kit 1.0 | 版面分析+表格+公式，输出 Markdown + content_list.json | 中 | GPU/大内存 CLI 子进程 | 复杂版式文本型 PDF |
| `mineru` | MinerU VLM | 端到端 VLM 解析，`vlm-engine` 后端 | 慢 | GPU | 与 paddlevl 同类的替代品 |
| `rapidocr` | RapidOCR | 纯 OCR 文字识别，无表格结构 | 快 | CPU | 简单扫描件 |
| `pymupdf` | PyMuPDF 文本层 | 仅提取文本层 | 最快 | 极低 | 数字原生 PDF（非扫描） |

设计取舍：

- 规范类 PDF 以表格、图文混排、扫描版居多，纯文本层提取（pymupdf）会丢表格语义，所以默认走视觉语言模型管线。
- 五条管线统一成单个开关 `RAG_DOCUMENT_PIPELINE`，不再支持旧的 `RAG_SCAN_PARSER`、`RAG_MINERU_BACKEND` 别名，降低配置歧义。
- 解析是 CPU/GPU 重操作但不常发生（每份文档一次），慢而准优于快而丢结构。

## PaddleOCR-VL 管线（默认）

- 服务地址：`RAG_PADDLEVL_API_URL`（默认 `http://127.0.0.1:8080`），由 `deploy/paddlevl/compose.yaml` 独立容器提供。
- `RAG_PADDLEVL_AUTO_START` 控制是否由后端自动拉起（Docker 部署时置 `false`，由 compose 统一管理）。
- 输入 PDF 整份上送，服务端完成版面分析、文本识别、表格结构还原。
- 解析超时由 `RAG_DOCUMENT_PARSE_TIMEOUT_SECONDS`（默认 1800s）控制。

## PDF-Extract-Kit 管线

`RAG_DOCUMENT_PIPELINE=pdf-extract-kit` 时调用 OpenDataLab pipeline 全量解析，文本型和扫描型 PDF 都交给它。输出中被纳入可检索文本的字段：

- `text`
- `table_caption` / `table_body` / `table_footnote`
- `img_caption` / `image_caption` / `img_footnote` / `image_footnote`
- `img_path` / `image_path`

## PyMuPDF fallback

`NativePdfParser` 使用 `page.get_text("text")` 和 `page.get_text("blocks", sort=True)` 提取文本块，并把每页写入 Markdown 注释：

```text
<!-- PDF_PAGE:1 -->
```

速度最快，但只作为解析服务不可用时的文本型 PDF 兜底。

## RapidOCR fallback

`inspect_pdf()` 抽样多页文本层，有效文本页不足则判定为扫描型 PDF。`RAG_DOCUMENT_PIPELINE=rapidocr` 时：

- 按 `RAG_OCR_RENDER_DPI` 渲染单页，单页 OCR，避免一次性加载整本文档。
- 过滤低置信度文本，按 bbox 的 y、x 顺序重排文本行。

## 结构化字段

| 字段 | 含义 |
| --- | --- |
| `page` | PDF 物理页码，从 1 开始 |
| `text` | 当前块文本 |
| `block_type` | 文本、图片、表格等类型 |
| `bbox` | 页面坐标，用于保留阅读顺序和版面信息 |
| `level` | 部分解析器返回的标题层级 |
| `printed_page` | 纸面页码，通常来自页脚 |
| `images` | 当前块关联的图片列表，主要用于表格内图片和普通图片预览 |

### 表格内图片结构

表格 HTML 中的 `<img src="...">` 会被抽出写入 `PageBlock.images`：

```json
{
  "page": 2,
  "type": "table",
  "text": "表格标题：续附表2 ...",
  "images": [
    {
      "path": "images/c0fb25e6....jpg",
      "caption": "橡檩屋顶截面",
      "row_context": "屋顶承重构件",
      "column_context": "截面图和结构厚度或截面最小尺寸(mm)",
      "cell_text": "橡檩屋顶截面0.50轻型木桁架屋顶截面",
      "order": 1
    }
  ]
}
```

| 字段 | 含义 |
| --- | --- |
| `path` | 解析产物中的相对图片路径 |
| `caption` | 图片 caption；表格单元格内图片优先使用图片前后的邻近文字 |
| `row_context` | 图片所在行的上下文，通常来自首列或行标题 |
| `column_context` | 图片所在列的表头 |
| `cell_text` | 图片所在单元格的完整文本 |
| `order` | 同一单元格内图片顺序 |

这样"屋顶承重构件截面图"这类问题能把表格文字和对应图片关联起来，而不是只知道这一页有图片。

## 解析结果落盘

```text
storage/parsed/{document_id}/normalized.json
storage/parsed/{document_id}/document.md
```

`normalized.json` 是后续重建索引的稳定输入；`document.md` 用于人工排查解析质量。

## 重新解析已有文档

改了解析器、输出转换、OCR、表格解析或 `normalized.json` 生成逻辑时，只 `reindex` 不够，需要重新解析：

```powershell
curl.exe -X POST "http://127.0.0.1:8008/api/documents/{document_id}/reparse" `
  -F "file=@E:\docs\updated.pdf"
```

它替换 `storage/uploads/{document_id}.pdf` 并重跑完整链路。查任务进度：

```powershell
curl.exe http://127.0.0.1:8008/api/jobs/{job_id}
```

只改了切分、检索词、重排或向量写入逻辑时，用 `reindex` 复用已有 `normalized.json` 即可。

## 运维思考

| 维度 | 考量 |
| --- | --- |
| 高并发 | 解析走 `RAG_MAX_WORKERS`（默认 1）串行队列：解析是最重的一步，并发多份大 PDF 会同时打爆解析服务和内存，宁可排队 |
| 时间 | 一份 600 页规范全量解析为分钟级（PaddleVL GPU 推理）；解析超时上限 1800s；上传后前端轮询任务进度而非阻塞等待 |
| 显存/内存 | PaddleVL / MinerU VLM 需要独立 GPU 服务（compose 单独编排，与 vLLM 模型服务分卡或分时复用）；PyMuPDF/RapidOCR 只需 CPU |
| 失败恢复 | 解析失败文档状态置 FAILED，错误写入 `documents.error`；`reparse` 可重跑；任务崩溃后 `recover()` 会重新入队 |
| 成本 | 解析只发生一次并落盘 `normalized.json`，之后 reindex/换 Embedding 都复用它，不重复消耗 GPU |

## 常见问题

- PDF 页数超过 `RAG_MAX_PDF_PAGES`（默认 600）解析前直接失败。
- 扫描件识别质量受渲染 DPI、图片清晰度、表格复杂度影响。
- 纸面页码和 PDF 物理页码不是同一概念，引用跳转使用 PDF 物理页码。
- 表格以 `normative_table` / `commentary_table` 入库；图片以 `normative_image` / `commentary_image` 入库。
- 表格内图片的 `images` 结构只有重新解析后才会写入旧文档的 `normalized.json`。

## 关键配置

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `RAG_DOCUMENT_PIPELINE` | `paddlevl` | 唯一的解析管线开关 |
| `RAG_PADDLEVL_API_URL` | `http://127.0.0.1:8080` | PaddleVL 服务地址 |
| `RAG_PADDLEVL_AUTO_START` | `true` | 是否自动拉起本地解析服务 |
| `RAG_MAX_PDF_PAGES` | `600` | PDF 页数上限 |
| `RAG_OCR_RENDER_DPI` | `180` | OCR 渲染 DPI |
| `RAG_DOCUMENT_PARSE_TIMEOUT_SECONDS` | `1800` | 单次解析超时 |
| `RAG_MINERU_COMMAND` | 空 | MinerU CLI 路径 |
| `RAG_MINERU_METHOD` | `auto` | MinerU 解析 method |

修改 `.env` 后需要重启后端。
