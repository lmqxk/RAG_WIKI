# 入库流水线

主要文件：

- `backend/src/backend/ingestion.py`
- `backend/src/backend/service.py`
- `backend/src/backend/repository.py`

## 模块定位

文档入库模块负责编排 PDF 从上传文件到可检索知识库的全过程，包括任务状态、解析、切分、索引写入和失败恢复。

## 技术实现

| 能力 | 实现 |
| --- | --- |
| 异步后台任务 | `ThreadPoolExecutor` |
| 上传分块读取 | `UploadFile.read(1024 * 1024)` |
| 重复文件识别 | SHA-256 |
| 任务状态 | SQLite `jobs` 表 |
| 文档状态 | SQLite `documents` 表 |
| 结构化产物 | `normalized.json` + `document.md` |
| 索引写入 | SQLite FTS5 + Qdrant |

## 上传入口

`RagService.upload()` 负责：

- 校验文件扩展名必须是 `.pdf`
- 按 1 MB 分块读取上传内容
- 计算 SHA-256，识别重复文件
- 按文件名推断标题、规范编号、版本
- 创建 `documents` 记录
- 创建 `jobs` 记录
- 提交后台入库任务

## 入库任务流程

```text
QUEUED
  -> RUNNING / preflight
  -> RUNNING / parsing
  -> RUNNING / chunking
  -> RUNNING / indexing
  -> COMPLETED / completed
```

失败时任务与文档分别进入 `FAILED`，错误信息写入 `documents.error` 和 `jobs.error`。

文档状态同步变化：

```text
QUEUED -> PARSING -> INDEXING -> READY
```

## Pipeline 细节

`IngestionManager._process()` 的关键阶段：

1. `preflight`：读取任务和文档记录，检查 PDF 文件路径。
2. `parsing`：调用 `DocumentParser.parse()`，实时更新解析进度。
3. `save_parsed`：落盘 `normalized.json` 和 `document.md`。
4. `chunking`：调用 `build_chunks()` 生成 `Chunk`。
5. `repository.replace_chunks()`：重写 SQLite chunks 和 FTS5。
6. `vector_index.replace_document()`：重写 Qdrant points（调用 Qwen3-Embedding 生成向量）。
7. `READY`：文档进入可检索状态。

## 任务恢复

应用启动时会调用 `IngestionManager.recover()`：

- 把上次异常退出时仍为 `RUNNING` 的任务重新置为 `QUEUED`
- 按创建时间重新提交等待任务

## 重新解析

`POST /api/documents/{document_id}/reparse` 用于替换已上传 PDF，并对同一个文档 ID 重新执行完整入库链路：

```text
替换 storage/uploads/{document_id}.pdf
  -> 重置 documents 状态为 QUEUED
  -> 创建新的 jobs 记录
  -> 调用 IngestionManager.submit()
  -> 重新解析、切分、写入 SQLite FTS5 和 Qdrant
```

如果该文档已有 `QUEUED` 或 `RUNNING` 任务，接口返回冲突错误，避免两个后台任务同时改同一份文档。

## 重建索引

`POST /api/documents/{document_id}/reindex` 复用：

```text
storage/parsed/{document_id}/normalized.json
```

不会重新解析 PDF，只重新执行切分和索引写入，适合调整切分规则后的快速验证。换 Embedding 模型后的全库重建用 `scripts/rebuild_vectors.py`（复用数据库 chunk ID，Wiki 锚点不受影响）。

## 图片结构入库

`normalized.json` 保存每个 `PageBlock` 的 `images` 字段（图片路径、caption、表格行/列上下文、单元格文本）。`reindex` 会读取并重新切分、索引，同时刷新该文档从解析产物派生的 Wiki 页面。旧文档的 `normalized.json` 若无 `images`，需要走 `reparse` 重新解析。

## 运维思考

| 维度 | 考量 |
| --- | --- |
| 高并发 | `RAG_MAX_WORKERS` 默认 1：解析+向量化是重操作，串行化避免同时打爆 PaddleVL 服务、内存和 vLLM；任务多时排队而非并行 |
| 时间 | 单文档入库 = 解析（分钟级）+ 切分（秒级）+ 向量化（约 2000 chunks 打 vLLM 批量接口，约 1 分钟）；全链路进度可通过 jobs 接口轮询 |
| 显存 | 入库期向量请求会与在线问答的 embedding 请求共享同一个 vLLM 容器，靠 vLLM continuous batching 消化，无需独立扩容 |
| 一致性 | `replace_chunks()`（SQLite）与 `replace_document()`（Qdrant）是重建索引的配对操作，二者必须一起成功；失败任务通过状态机 + recover() 保证不产生半入库悬挂文档 |
| 幂等 | 重复上传通过 SHA-256 识别；同文档重复 reindex/reparse 通过任务冲突检查挡住 |

## 维护注意

- 入库线程数由 `RAG_MAX_WORKERS` 控制，当前默认是 1，避免大 PDF 并发时抢占内存。
- `replace_chunks()` 和 `replace_document()` 是重建索引的核心配对，二者要保持一致。
- 如果调整解析结果格式，需要同步更新 `_save_parsed()` 和 `_reindex()` 的读取逻辑，尤其是 `PageBlock.images` 这类结构化字段。
- Docker 部署下 Qdrant 为服务化容器（`RAG_QDRANT_URL`），本地开发模式与容器模式共用 `storage/`，但不要同时运行两套后端指向同一份数据。
