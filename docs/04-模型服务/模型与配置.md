# 模型与配置

主要文件：

- `backend/src/backend/config.py`
- `backend/src/backend/providers.py`
- `.env.example`

## 模块定位

模型与配置模块负责集中读取运行参数（`RAG_` 前缀统一命名，`.env` + 环境变量覆盖），并适配回答生成、向量化和重排三类模型服务。所有模型接口均走 OpenAI 兼容协议，切换供应商只改 `.env`。

## 全链路模型一览


| 环节                | 推荐模型              | 部署方式                             | 协议                           |
| ------------------- | --------------------- | ------------------------------------ | ------------------------------ |
| 回答生成            | DeepSeek-V4 / Qwen 等 | 外部 API（硅基流动/火山引擎/自建）   | OpenAI 兼容`/chat/completions` |
| 检索规划（Planner） | 复用回答模型          | 同上                                 | OpenAI 兼容，输出 JSON 计划    |
| 向量化              | Qwen3-Embedding-0.6B  | vLLM 容器（GPU） / 外部 API fallback | OpenAI 兼容`/embeddings`       |
| 重排                | Qwen3-Reranker-0.6B   | vLLM 容器（GPU） / 外部 API fallback | `/v1/rerank`                   |

> 本地无 GPU 时，Embedding 可降级为 BM25 纯词法检索，问答功能不受影响。

## 常用配置


| 变量                                                                       | 说明                               |
| -------------------------------------------------------------------------- | ---------------------------------- |

| `RAG_CHAT_MODEL` / `RAG_CHAT_MAX_TOKENS` / `RAG_CHAT_THINK`                | 回答模型、最大输出 token、思考开关 |
| `RAG_EMBEDDING_BACKEND` / `RAG_EMBEDDING_BASE_URL` / `RAG_EMBEDDING_MODEL` | 向量服务接入                       |

| `RAG_RERANK_BASE_URL` / `RAG_RERANK_MODEL`                                 | 重排服务接入                       |

## 回答生成

`ChatProvider` 把检索资料整理成带编号的资料包，调用 OpenAI 兼容的 `/chat/completions`：

```json
{
  "model": "deepseek-v3",
  "temperature": 0.1,
  "max_tokens": 2048,
  "messages": [
    {"role": "system", "content": "系统提示词"},
    {"role": "user", "content": "问题和证据"}
  ]
}
```

未配置回答模型时，系统退化为摘录式回答：事实类问题返回最相关原文依据，对比类问题按文档分组展示证据。

### 对比资料包

对比类问题使用按文档分组的资料包（`evidence_payload`），`documents[].items[].id` 仍对应前端引用编号 `[1]`、`[2]`，分组只是让模型稳定区分新旧规范，避免混成一段回答。提示词要求对比回答优先包含：结论（是否直接可比）、对比要点（分列各文档数值/条件/资料编号）、资料不足说明。

回答后端不做正则清理，只保留首尾空白裁剪；内部图片路径在传给 LLM 前替换为 `[图片见资料预览]`。

### Token 配置实验结论

`RAG_CHAT_MAX_TOKENS=2048`：实验中降到 1024 时跨文档对比、长条款归纳容易被截断。Planner 只输出短 JSON 计划，应单独设小配额，不为压缩 Planner 而降低最终回答上限。

### 双端点回退

回答模型支持主备双端点。当 `RAG_OPENAI_BASE_URL_1` / `RAG_OPENAI_API_KEY_1` / `RAG_CHAT_MODEL_1` 同时配置时，1 号端点作为主服务，原 `RAG_OPENAI_BASE_URL` 自动转为 fallback。单端点故障不阻断问答。

## 向量化

`EmbeddingProvider` 模式：


| `RAG_EMBEDDING_BACKEND` | 行为                                                                  |
| ----------------------- | --------------------------------------------------------------------- |
| `openai`                | 调 vLLM 容器或外部 API 的`/embeddings`，Qwen3-Embedding-0.6B，1024 维 |
| `local`                 | 进程内加载本地模型（bge-small-zh-v1.5，512 维）                       |
| `hash`                  | 确定性哈希向量，仅离线调试（正式评估禁用）                            |

维度校验：返回向量长度与 `RAG_EMBEDDING_DIMENSION` 不一致时直接抛错，防止错维度向量写进 Qdrant。

多级回退链（可在 config 关闭）：主服务 → Jina API → 硅基流动（bge-large-zh）→ HF Inference。生产环境建议关闭 fallback，故障时显式降级为 BM25 词法检索而非静默换模型（避免不同量纲向量混存）。

### Qwen3 查询模板

非对称检索的官方要求（实现见 `providers.py::_query_instruction`）：

```text
Instruct: Given a web search query, retrieve relevant passages that answer the query
Query: {用户问题}
```

文档侧不加前缀。详细技术说明见《Docker与vLLM技术细节》。

## 重排

`RerankProvider` 回退链：

```text
Qwen3-Reranker（vLLM 容器 / 外部 API，主）
  -> 硅基流动 bge-reranker-v2-m3（云端 fallback，可关）
  -> 本地词项重合度排序（兜底，永不失效）
```

任何一层失效都不阻断问答。Rerank 请求：

```json
{
  "model": "qwen3-reranker",
  "query": "<query 模板>",
  "documents": ["候选文档"],
  "top_n": 8,
  "return_documents": false
}
```

### Agentic Planner LLM

规划层复用回答模型配置（`RAG_OPENAI_BASE_URL` / `RAG_CHAT_MODEL`），只输出 JSON 检索计划，不生成最终回答。代码用 Pydantic 校验 JSON，限制工具名（`search_general` / `search_in_document` / `search_wiki`）和文档引用；规划失败回退本地规则计划，检索仍能完成。

关键默认值（`config.py`）：

```python
agentic_retrieval_enabled = True
agentic_planner_llm_enabled = True
agentic_max_steps = 4
agentic_parallel_workers = 4
agentic_min_hits = 4
```

## 流式回答与日志

问答优先走 `/api/chat/stream` 流式返回，指标写入 `storage/logs/chat-metrics.jsonl`：


| 字段                       | 含义                         |
| -------------------------- | ---------------------------- |
| `planner_ms`               | Planner LLM 制定检索计划耗时 |
| `recall_ms`                | 并行召回和补充检索耗时       |
| `rerank_ms`                | 最终一次重排耗时             |
| `answer_llm_ttft_ms`       | 检索完成到回答首 token 耗时  |
| `first_token_ms`           | 请求开始到首 token 总耗时    |
| `total_ms`                 | 整个流式请求耗时             |
| `citations` / `query_type` | 引用数量与问题类型           |

## 运维思考


| 维度         | 考量                                                                                                                                    |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 时延预算     | 一次问答 ≈ Planner（几百 ms）+ 召回（<100ms）+ rerank（100~300ms）+ LLM 首 token（取决于 API 模型）；`chat-metrics.jsonl` 分段定位慢点 |
| 高并发       | 回答模型 API 是并发瓶颈（受服务商限流）；embedding/rerank 由 vLLM batching 消化                                                         |
| 成本         | API 成本主要在回答生成；Planner 输入仅文档目录 + Wiki metadata（数百 token），成本可忽略                                                |
| 模型替换成本 | 回答/向量化/重排均走 OpenAI 兼容协议，换模型只改`.env`；向量模型替换必须换 Qdrant 集合并重建索引                                        |
| 密钥安全     | 密钥只放`.env`，不写入代码、README 或测试文件；`.env` 不入 git                                                                          |
| 配置分层     | 默认值放`config.py`（版本管理），`.env` 只放密钥、地址和临时覆盖项                                                                      |

## 维护注意

- 修改 `.env`、密钥、token、API 地址前必须先确认影响范围。
- 更换 Embedding 模型或维度后，必须使用新的 Qdrant 集合并对历史文档重建索引。
- 关闭 fallback 可避免不同量纲向量静默混入索引；故障时降级 BM25 更可控。
