# 存储与索引

主要文件：

- `backend/src/backend/db.py`
- `backend/src/backend/repository.py`
- `backend/src/backend/vector_index.py`

## 模块定位

存储与索引模块负责保存文档元数据、任务状态、文本块、全文检索数据和向量索引数据，是整个系统的持久层。设计原则：**结构化数据归 SQLite，全文归 FTS5，向量归 Qdrant，三者以 chunk_id 关联**。

## 存储选型对比

| 存储 | 承担职责 | 替代方案 | 不采用替代方案的原因 |
| --- | --- | --- | --- |
| SQLite（WAL） | 文档/任务/chunk 元数据 | PostgreSQL/MySQL | 单机部署零运维，WAL 读写并发够用；数据量（千级文档、万级 chunk）远未到需要独立数据库服务的规模 |
| SQLite FTS5 | 全文检索 | Elasticsearch | 中文需要外接分词器，ES 部署重；FTS5 + 二元字串对规范术语/条款号检索效果足够 |
| Qdrant | 向量索引 | FAISS / Milvus | FAISS 无持久化管理且并发写弱；Milvus 太重。Qdrant 单容器即可跑、payload 过滤、HNSW 成熟，与本系统规模匹配 |

三种存储的组合收益：全部数据落在 `storage/` 目录，**备份 = 复制一个文件夹**，且支持无 Docker 的本地开发模式与 Docker 部署模式共用同一份数据。

## SQLite

默认数据库路径：`storage/rag.db`，启用 WAL 模式便于读写并发。

核心表：

| 表 | 作用 |
| --- | --- |
| `documents` | 文档元数据（标题、标准号、版本、页数）和处理状态 |
| `jobs` | 后台任务状态和错误信息 |
| `chunks` | 切分后的文本块（含 clause_no、chapter_path、页码锚点） |
| `chunks_fts` | SQLite FTS5 全文索引虚拟表 |

核心索引：

```sql
CREATE INDEX IF NOT EXISTS idx_documents_status ON documents(status);
CREATE INDEX IF NOT EXISTS idx_jobs_document ON jobs(document_id);
CREATE INDEX IF NOT EXISTS idx_chunks_document ON chunks(document_id);
CREATE INDEX IF NOT EXISTS idx_chunks_clause ON chunks(clause_no);
```

### FTS5 全文索引

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS chunks_fts USING fts5(
    chunk_id UNINDEXED,
    document_id UNINDEXED,
    clause_no,
    chapter_path,
    terms,
    tokenize = 'unicode61'
);
```

`repository.search_terms()` 负责生成适合 FTS5 的检索词：

- 英文、数字、规范编号保留为词项
- 中文使用二元字串（bigram），规避 FTS5 无中文分词的问题
- 条款号、章节路径、正文共同进入索引

## Qdrant 向量索引

| 项 | 值 |
| --- | --- |
| 部署形态 | Docker 容器 `rag-zb-qdrant`（v1.16.2），HTTP 6333 |
| 集合名 | `document_chunks_qwen3_embedding_v1`（按 Embedding 模型版本隔离） |
| 距离度量 | COSINE |
| 向量维度 | 1024（Qwen3-Embedding-0.6B） |
| point id | chunk.id（UUID），与 SQLite chunks 主键一致 |
| payload | `document_id`（检索时用于文档范围过滤） |

连接模式由 `RAG_QDRANT_URL` 决定：

- **本地开发**：未配置时使用嵌入式模式（`QdrantClient(path=storage/qdrant)`），无需任何容器。
- **Docker 部署**：配置 `http://qdrant:6333`（compose 内部服务名）或宿主机 `http://127.0.0.1:6333`。

### 写入策略

`replace_document()` 对单文档索引重建采用**先删后写**：

1. 按 `document_id` payload 过滤删除该文档全部旧 points（wait=true 确保落盘）
2. 按 32 条/批调用 Embedding 后 upsert
3. 文档侧输入拼接 `chapter_path + clause_no + text`，让向量携带结构上下文

集合按 Embedding 模型命名隔离（`document_chunks_qwen3_embedding_v1`），换模型直接换集合，避免新旧量纲向量混存导致检索错乱。

## 索引重建方法

修改切片、检索词生成、重排逻辑或向量写入逻辑后，已上传文档不会自动应用新规则。需要先重启后端让新代码生效，再调用重建接口。

**单文档重建**（复用 `normalized.json`，不重新解析 PDF）：

```powershell
curl.exe -X POST http://127.0.0.1:8008/api/documents/{document_id}/reindex
```

**全库向量重建**（换 Embedding 模型后，复用数据库 chunk ID，Wiki 锚点不受影响）：

```powershell
backend\.venv\Scripts\python.exe scripts\rebuild_vectors.py
```

**重新解析**（改了 PDF 解析器、OCR 或 normalized.json 生成逻辑时必须走这条）：

```powershell
curl.exe -X POST http://127.0.0.1:8008/api/documents/{document_id}/reparse -F "file=@E:\docs\updated.pdf"
```

| 场景 | 接口/脚本 | 是否重新解析 PDF | chunk ID 是否变化 |
| --- | --- | --- | --- |
| 调整切分/检索词生成 | `reindex` | 否 | 变（Wiki 需刷新） |
| 更换 Embedding 模型 | `scripts/rebuild_vectors.py` | 否 | 不变 |
| 调整解析逻辑/换源文件 | `reparse` | 是 | 变 |

排查是否仍是旧索引时，可查该文档当前 chunk 数量：

```powershell
.\backend\.venv\Scripts\python.exe -c "import sqlite3; con=sqlite3.connect('storage/rag.db'); doc='<document_id>'; print(con.execute('select count(*) from chunks where document_id=?',(doc,)).fetchone()[0])"
```

## 运维思考

| 维度 | 考量 |
| --- | --- |
| 容量 | 全库约 2000+ chunks；1024 维 float32 单向量约 4KB，向量总量约 10MB 级，SQLite 同量级——内存与磁盘压力可忽略，无需提前做分布式设计 |
| 并发写 | SQLite WAL 支持读写并发，但 Qdrant 同一集合同一时间只允许一个后端进程写入；**严禁两套后端同时指向同一份 storage/** |
| 写放大 | reindex 是整文档先删后写，2000 chunks 约几十秒（主要是 Embedding 计算），不做增量 diff——规范文档是低频更新场景，简单可靠优先 |
| 备份恢复 | 全部状态在 `storage/`：rag.db + qdrant-server/ + parsed/ + uploads/；冷备份直接复制目录，热备份建议先停后端 |
| schema 变更 | 数据库结构变更属于高风险操作，需要先备份并确认影响范围 |

## 维护注意

- 不要手动编辑 `storage` 下的数据文件，除非已经备份并明确知道影响范围。
- Embedding 维度或模型改变必须使用新的 Qdrant 集合名，并对历史文档执行重建。
- 重复启动后端可能遇到 Qdrant 存储锁冲突，先确认没有残留进程。
- 数据排查只读检查：`sqlite3 storage\rag.db ".tables"`；不要在生产数据上直接执行 `DELETE`、`DROP`、`UPDATE`。
