# 混合检索

主要文件：

- `backend/src/backend/retrieval.py`
- `backend/src/backend/repository.py`
- `backend/src/backend/vector_index.py`
- `backend/src/backend/providers.py`

## 模块定位

检索模块负责根据用户问题从知识库召回最相关的条款证据，并交给 Reranker 精排，是回答质量的直接决定环节。核心思路是 **Hybrid Retrieval（词法 + 语义双路召回）+ RRF 融合 + 神经重排**。

## 检索方案选型对比

| 方案 | 召回特点 | 弱点 | 本项目结论 |
| --- | --- | --- | --- |
| 纯 BM25 / FTS5 | 条款号、标准号、数值、术语精确命中强 | 同义改写召回不了（“防火间距”≠“间距要求”） | 作为第一路召回保留 |
| 纯向量检索 | 语义改写鲁棒 | 条款号/数值这类精确匹配反而不如词法 | 作为第二路召回保留 |
| 混合检索 + RRF | 两路互补，单路漏召回由另一路兜底 | 融合只看排名，需要重排模型压轴 | **采用** |
| 混合 + 交叉编码重排 | 精排阶段 query-doc 联合编码，精度最高 | 增加一次模型调用（约 100~300ms） | **采用**（Qwen3-Reranker） |

规范类问答的关键洞察：提问里往往带精确标识（`4.1.4`、`GB55037-2022`、`0.25h` 耐火极限），这类信息词法检索碾压语义检索；而“新旧规范对厂房防火间距的要求差异”这类自然语言问法又必须靠语义。单路必丢，所以混合是必然选择。

## 查询类型识别

`query_type()` 会把问题粗分为四类，决定后续检索策略：

| 类型 | 触发条件 | 检索行为 |
| --- | --- | --- |
| `clause` | 包含 `4.1.4` 这类条款号 | 优先精确查条（exact 通道），正文条款优先 |
| `comparison` | 包含对比、比较、新旧、差异等词 | 多文档分别召回 + 文档间平衡（见 AgenticRAG 文档） |
| `summary` | 包含总结、汇总、要求等词 | 主题归纳，倾向覆盖多章节 |
| `fact` | 默认类型 | 常规混合检索 |

## 检索链路

```text
User Question
  -> query_type() / focused_query()          查询理解与聚焦
  -> exact clause search                     条款号精确通道
  -> BM25 / SQLite FTS5                      词法召回（top 20）
  -> Dense / Qdrant + Qwen3-Embedding        语义召回（top 20）
  -> Reciprocal Rank Fusion (k=60)           排名融合（top 20）
  -> Qwen3-Reranker 神经重排                  精排（top 8）
  -> Top-K Evidence -> LLM Answer
```

## RRF 融合

`reciprocal_rank_fusion()` 实现思想：

```text
score(chunk) = Σ_routes 1 / (k + rank_route(chunk))    # k = 60
```

为什么用 RRF 而不是加权分数求和：

- BM25 分数（无界）和余弦相似度（0~1）**量纲不同**，直接加权需要调权重且不稳定。
- RRF 只看每路的**排名**，天然对分值尺度免疫，k=60 是社区通用默认值（压制头部排名差距，避免单路第 1 名独大）。
- 两路都命中的 chunk 分数叠加，天然奖励“词法+语义双确认”的证据——这正是规范条款的理想特征。

融合时代码还保留了一个细节：同一 chunk 在两路都出现时，若任一路来源是 `exact`（条款号精确命中），保留 exact 版本的元数据，保证引用定位不被覆盖。

## 向量语义检索

| 项 | 值 |
| --- | --- |
| Embedding 模型 | Qwen3-Embedding-0.6B（vLLM 容器，端口 8010） |
| 向量维度 | 1024 |
| 相似度 | COSINE |
| Qdrant 集合 | `document_chunks_qwen3_embedding_v1` |
| Query 侧处理 | 非对称模型要求加 Instruct 前缀（见《模型与配置》） |
| Document 侧输入 | `chapter_path + clause_no + text` 拼接，让向量同时携带结构上下文 |

Embedding 服务不可用时**不静默降级**：健康接口显示 embedding 未就绪，稠密检索退化为纯 BM25 词法模式（问答仍可用，语义召回变弱）。只有显式设置 `embedding_backend=hash` 才用哈希向量做离线调试。

## 重排（Rerank）

融合后 top 20 候选交给 Qwen3-Reranker-0.6B（vLLM 容器，端口 8011）做交叉编码精排，取 top 8 进入回答生成。

重排价值：召回阶段的 embedding 是**双塔**结构（query 和 doc 独立编码），快但交互浅；重排是**交叉编码**（query 和 doc 拼接后联合编码），能判断“该条款是否真的回答了这个问题”，对“问 A 但召回了相邻的 B 条款”这类边界样本矫正明显。

失败链路：Qwen3-Reranker 主服务 → （可选）硅基流动 fallback → 本地词项重合度排序，任何一层失效都不阻断问答。

## 图片资料预览

回答引用携带 `preview_image_url`，选择逻辑在 `backend/src/backend/service.py::preview_from_parsed()`：

- 优先读取 `storage/parsed/{document_id}/normalized.json` 中当前页附近的 `images`。
- 对图片的 `caption`、`row_context`、`column_context`、`cell_text` 和用户问题做词项匹配。
- 命中表格内结构化图片则返回对应资源 URL；无结构化 `images` 时回退到 `content_list.json` 的 `img_path`。

前端按回答正文中的引用编号选图（回答引用 `[4]` 时优先展示第 4 条资料的预览图）。

## 关键配置

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `RAG_RETRIEVAL_BM25_TOP_K` | `20` | BM25 候选数 |
| `RAG_RETRIEVAL_DENSE_TOP_K` | `20` | 向量候选数 |
| `RAG_RETRIEVAL_FUSED_TOP_K` | `20` | RRF 融合后候选数 |
| `RAG_RETRIEVAL_FINAL_TOP_K` | `8` | 重排后最终证据数 |
| `RAG_ANSWER_MAX_CITATIONS` | `6` | 返回引用上限（实际按正文引用编号过滤） |

漏斗 20/20 → 20 → 8 的设计逻辑：融合后 20 保证重排有足够候选区分度；最终 8 条是 LLM 上下文预算和证据噪声的平衡——证据太少回答片面，太多会稀释注意力且引用编号稀疏。

## 运维思考

| 维度 | 考量 |
| --- | --- |
| 时延 | 单次检索 = FTS5（<10ms）+ embedding（约 20~50ms，vLLM 批处理）+ rerank（约 100~300ms，取决于候选长度）；rerank 是检索链路最贵一环，因此只在融合后对 top 20 调用一次，不做多轮 |
| 高并发 | FTS5/Qdrant 天然并发安全；embedding/rerank 靠 vLLM continuous batching 消化并发，多问并发时延亚线性增长 |
| 显存 | 检索链路本身无显存，向量计算全部卸载到 vLLM 容器（embedding 0.2 显存利用率 + reranker 0.2，见《Docker与vLLM技术细节》） |
| 观测 | 流式问答耗时写入 `storage/logs/chat-metrics.jsonl`：`retrieval_ms`、`first_token_ms`、`total_ms`、`citations`、`query_type`，可定位慢在召回还是重排 |
| 调参验证 | 调整检索参数后，用条款查询、主题总结、新旧对比三类问题分别回归验证 |

## 维护注意

- 对规范类问题，精确条款和术语匹配通常比泛语义召回更可靠，改融合逻辑时不要削弱 exact 通道。
- 短标题（如“规范”）容易误命中文档识别，文档解析会忽略过短标识，优先使用标准号和版本。
- 更换 Embedding 模型或维度后必须重建 Qdrant 集合并 `reindex`（见《存储与索引》）。
