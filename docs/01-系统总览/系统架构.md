# 系统架构

## 模块定位

本项目是面向规范、标准、制度、法规类 PDF 的知识库问答系统（规智库）。产品形态为"知识库模式"：用户上传 PDF，系统解析、入库、建立索引后，在 Web 工作台中按已选文档范围提问，返回带原文引用的回答。

## 全景地图

一屏总览系统全貌（树状图，深度阅读跳转文末「模块文档索引」）：

```text
规智库（Document Intelligence + RAG Agent）
│
├─ 01 产品与交互
│   ├─ 知识库模式：上传单份 PDF / 选择一或多份规范 / 自然语言问答
│   ├─ 问答类型：条款精确查询 / 主题总结 / 跨文档综合 / 新旧规范对比
│   ├─ 证据交互：行内 [n] 引用（点击弹原文资料面板）/ 正文与条文说明标识 / PDF 页码跳转
│   └─ Web 前端：Next.js + React 19 + TS + Tailwind；智能问答 / 知识库 / Wiki 工作区三视图
│
├─ 02 API 与应用服务（FastAPI，Docker :8008）
│   ├─ 接口：健康检查 / 文档上传列表 / 任务进度 / 问答（同步+SSE 流式）/ 重解析重索引
│   ├─ RagService：文件哈希去重 / 元数据推断 / 检索编排 / 引用封装
│   ├─ IngestionManager：单工作线程 / 持久化任务状态 / 失败恢复 / 复用解析结果
│   ├─ WikiManager：整文档分批概念抽取 / 概念页与 related 图 / search_wiki 供 Planner 调用
│   └─ 模型 Provider（多级降级）：火山方舟 deepseek-v4-flash（主）→ Ollama（备）；
│       Qwen3-Embedding/Reranker（vLLM 容器）→ 硅基流动（云端备）→ 离线证据回答
│
├─ 03 文档理解 Pipeline
│   ├─ 上传预检：PDF 格式 / ≤100 MB / ≤600 页 / SHA-256 去重
│   ├─ 默认解析：PaddleOCR-VL 视觉语言模型管线；可切 pdf-extract-kit / mineru / rapidocr / pymupdf
│   └─ 统一输出：document.md / normalized.json（复用：换切块换模型不重解析）/ PageBlock 模型
│
├─ 04 结构化切片
│   ├─ 结构识别：章节 / 条款 / 正文 / 表格 / 图片元数据；前置页状态机（目录版权页不入索引）
│   ├─ 来源分区：规范正文 normative / 条文说明 commentary（单向状态机）/ 表格图片后缀
│   └─ 切片策略：整条款聚合为主；超长按句切 + 重叠（#n 续块）；父子条款关系；页码保留
│
├─ 05 Hybrid RAG 检索
│   ├─ Query Understanding（确定性规则）：fact / clause / summary / comparison 分类与聚焦改写
│   ├─ Agentic Planner（LLM，thinking 关闭）：多维 Query 改写 / ≤5 步计划 / 并行执行 / 失败回退
│   ├─ 精确召回：条款号字段匹配 / 正文优先
│   ├─ 双路召回：BM25（FTS5 bigram）+ 向量（Qdrant + Qwen3-Embedding）
│   └─ 融合精排：RRF（k=60）→ Qwen3-Reranker 交叉编码（top 8）/ 正文加权 / 跨文档均衡
│
├─ 06 回答生成与引用
│   ├─ 证据约束 Prompt 七规则：封闭世界 / 强制溯源 / 编号校验 / 数值单位核对 / 表格过滤…
│   ├─ 解码约束：temperature=0.1，流式输出
│   ├─ 综合回答：对比题按文档分组（相同点 / 变化点 / 适用范围）
│   └─ 引用模型：文档名/标准号/版本/条款号/PDF 页码/原文摘录/相关性分数
│
├─ 07 数据与存储
│   ├─ SQLite：documents / jobs / chunks / wiki + FTS5 倒排索引（bigram）
│   ├─ Qdrant：集合 document_chunks_qwen3_embedding_v1，point id = chunk UUID
│   ├─ 文件系统：storage/uploads（保留子目录层级）/ parsed / wiki / logs（唯一日志目录）
│   └─ 当前边界：少量规范知识库（2170 chunks）、无登录多租户
│
├─ 08 运行与质量
│   ├─ 部署：Docker Compose 五容器（backend :8008 / frontend :3000 / qdrant :6333 /
│   │        embedding :8010 / reranker :8011，`--profile gpu` 可拆卸）
│   ├─ 开发：start.cmd 本地一键启动；scripts/deploy.ps1 自动检测 GPU
│   ├─ 容量实测：纯 API 100 并发 280 req/s（p99<500ms）；全链路 100 并发 4.58 req/s（100% 成功）
│   ├─ 观测：chat-metrics.jsonl 分阶段耗时；TTFT 15s→6.5s（Planner thinking 关闭）
│   └─ 质量：Ruff / Pytest / 前端生产构建 / 真实 PDF 端到端测试
│
└─ 09 后续演进
    ├─ 产品：登录与权限 / 批量上传 / 文档版本管理 / 管理后台
    ├─ 解析：表格公式专用模型 / 版面模型路由 / OCR 置信度人工校正
    ├─ 检索：独立 Elasticsearch / 评测集与召回指标
    └─ Agent：多跳检索 / 规范冲突检测 / 结论审计
```

## 总体链路

```text
PDF 上传
  -> API 接收并保存文件
  -> 创建文档记录和后台任务
  -> PaddleOCR-VL / PDF-Extract-Kit 解析
  -> 章节、条款、页码结构化
  -> 文本块切分
  -> SQLite 全文索引 + Qdrant 向量索引写入
  -> Wiki 派生层同步文档摘要、概念和原文锚点
  -> 用户提问
  -> Agent Planner 制定检索步骤
  -> 并行执行 BM25 + 向量召回
  -> 资料不足时补充检索
  -> 合并后统一重排序（Qwen3-Reranker）
  -> 模型生成或证据摘录
  -> 回答和引用返回 Web 端
```

| PDF 解析    | PaddleOCR-VL（默认）、PDF-Extract-Kit、MinerU VLM、PyMuPDF、RapidOCR | 按文档复杂度分级回退，见《文档解析》              |

| 重排        | Qwen3-Reranker-0.6B（vLLM 容器）                                 | 与 Embedding 同源部署，序列分类打分         |
| RAG 检索    | Agentic Planner、BM25、Vector Search、RRF、Reranker              | 自研轻量编排，不引入 LangChain            |
| Wiki 派生层  | 文档目录、概念页、chunk 锚点、related 图数据                                | 跨文档导航与规划上下文                     |
| LLM 调用    | Ollama / OpenAI 兼容协议（火山方舟 deepseek-v4-flash 主链路）             | `RAG_OPENAI_BASE_URL` 可切换任意兼容服务 |
| 部署        | Docker Compose（含 GPU profile）                                | 组件可拆卸、任意机器可装                    |

## Document Intelligence + RAG Agent 设计

系统内部按两层理解：

- **Document Intelligence**：PDF document understanding，包括文本层识别、OCR、版面块提取、章节条款识别、表格处理、图片位置、页码映射和结构化落盘。

- **RAG Agent**：Query Understanding、Planner、多步 Hybrid Retrieval、补充检索、Rerank、证据组织、LLM 生成和引用回链。

这两个概念不出现在最终用户界面，但必须出现在工程文档中，便于拆模块、扩展模型和定位问题。

## 当前边界

- 定位是少量规范文件的单机知识库，不是多租户平台。

- 单个 PDF 上限由 `RAG_MAX_FILE_SIZE_MB` 和 `RAG_MAX_PDF_PAGES` 控制。

- 未配置外部模型时系统仍可返回检索证据（摘录式回答），但综合归纳能力受限。

- 问答默认由 `AgenticRetriever` 处理：LLM Planner 结合文档目录和 Wiki 摘要生成多个检索步骤，并行召回，资料不足时补检，最后统一重排序。

- `HybridRetriever.retrieve()` 仅在关闭 `agentic_retrieval_enabled` 时作为基础检索兜底。

- Wiki 是 `storage/parsed`、SQLite chunks 和 Qdrant 的派生导航层，最终回答以原文检索结果为依据。

## 运维思考

| 维度   | 现状与考量                                                                                                                                                                                |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 部署形态 | Docker Compose 五容器（qdrant / backend / frontend / embedding / reranker），GPU 模型服务挂 `--profile gpu` 可拆卸；无 GPU 机器自动降级 BM25 词法检索，问答不中断                                                    |
| 高并发  | 纯 API 层 100 并发 280 req/s（p99<500ms，Uvicorn 事件循环）；全链路 100 并发 4.58 req/s（100% 成功、无雪崩），瓶颈在每次问答的 2 次云端 LLM 调用而非检索架构；检索阶段 `agentic_parallel_workers=4` 并行，vLLM 侧 continuous batching 消化并发 |
| 时延   | TTFT 6.5s（Planner thinking 关闭后，原 15s）；检索召回+重排 <400ms；各阶段耗时有独立指标（见《模型服务》性能日志）                                                                                                         |
| 资源   | embedding/reranker 各占 GPU 20% 显存预算（0.6B 模型 bf16 权重约 1.2GB，加 KV/激活约 2\~3GB/容器）；12GB 单卡可同时跑双模型                                                                                         |
| 数据安全 | 业务数据全部落在项目 `storage/` 目录，容器无状态；模型缓存独立卷 `rag-zb-models`                                                                                                                               |
| 可观测性 | 运行日志 `storage/logs/backend.log`（滚动 10MB×5）；问答指标 `storage/logs/chat-metrics.jsonl`                                                                                                    |

## 维护原则

- 用户界面只展示产品语义，不展示内部技术链路；工程文档必须写清楚技术链路。

- 回答必须附引用，引用要能回到 PDF 原页。

- 条款号、页码、正文/说明区分是核心资产，解析和切分阶段不能随意丢。

- 后端配置统一走 `RAG_` 环境变量和项目根 `.env`，不要把密钥写进代码。
