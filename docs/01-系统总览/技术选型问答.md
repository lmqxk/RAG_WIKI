# RAG 链路技术选型问答

按「数据清洗 → 文本切分 → Embedding → 向量库 → 检索优化 → LLM 生成」六个环节，以 Q\&A 形式梳理每一步的技术决策与权衡。

## 链路总览

```text
PDF 上传
  → 解析与清洗（PaddleOCR-VL，多管线回退）
  → 结构感知切分（条款级 chunk，携带章节/页码/来源元数据）
  → 双索引（SQLite FTS5 + Qdrant 向量）
  → 检索：BM25 + 向量双路召回 → RRF 融合 → Qwen3-Reranker 精排
  → LLM 流式生成 → 带 [n] 引用的回答（可跳转 PDF 原页）
```

| 环节        | 选型                           | 一句话理由                 |
| --------- | ---------------------------- | --------------------- |
| 数据清洗 / 解析 | PaddleOCR-VL（四管线回退）          | 规范 PDF 表格图文混排，VLM 保结构 |
| 文本切分      | 结构感知（条款级）+ 滑窗兜底              | 条款 = 语义单元 = 引用锚点      |
| Embedding | Qwen3-Embedding-0.6B（1024 维） | 中文效果 + 指令感知 + 显存友好    |
| 向量库       | Qdrant                       | 单容器、payload 过滤、规模匹配   |
| 检索优化      | 混合召回 + RRF + 交叉编码重排          | 精确标识与自然语言问法并存         |
| LLM 生成    | Ollama / OpenAI 兼容（流式）       | 协议开放、可替换、可降级          |

## Q1 数据清洗：为什么用视觉语言模型解析，而不是直接抽 PDF 文本层？

**A**：建筑工程规范 PDF 有三个特征：表格密集（大量参数在表格里）、图文混排、扫描版占比高。直接抽文本层（PyMuPDF）会丢表格结构，等于丢掉规范的核心信息，因此默认走 PaddleOCR-VL 视觉语言模型管线，版面分析、表格还原、OCR 一体完成。

清洗不只是字符串过滤，而是解析层的结构化规则：

- **前置页识别**：目录、公告、版权页进入 `front_matter` 区，不入检索索引；

- **水印过滤**：URL 型水印正则剔除；

- **OCR 置信度过滤**：低置信度文本不进入索引；

- **阅读顺序重排**：按 bbox 坐标（y→x）恢复版面顺序。

另有 pdf-extract-kit、MinerU、RapidOCR、PyMuPDF 四条管线按文档复杂度回退，由 `RAG_DOCUMENT_PIPELINE` 单开关切换：

| 管线              | 速度          | 适用            |
| --------------- | ----------- | ------------- |
| paddlevl（默认）    | 分钟级/百页（GPU） | 扫描件、复杂表格、图文混排 |
| pdf-extract-kit | 中           | 复杂版面文本型       |
| rapidocr        | 快（CPU）      | 简单扫描件         |
| pymupdf         | 最快          | 数字原生 PDF 兜底   |

解析结果落盘 `normalized.json` 作为稳定中间产物：后续调整切分、更换 Embedding、重建索引都复用它，不重复消耗 GPU——解析是每文档一次性的离线操作，慢而准优于快而丢结构。

## Q2 文本切分：为什么按条款结构切，而不是固定长度滑窗？块大小和重叠度怎么定？

**A**：核心判断：**规范文本的天然粒度不是段落，是条款**——一个条款 = 一个语义单元 = 一个引用锚点。

| 策略     | 优点           | 缺点           | 结论      |
| ------ | ------------ | ------------ | ------- |
| 固定长度滑窗 | 实现简单、长度均匀    | 切断条款语义、引用定位差 | 仅作长文本兜底 |
| 递归字符分割 | 通用           | 不理解规范文体      | 不采用     |
| 结构感知切分 | 条款/章节/表格语义完整 | 依赖解析质量       | **采用**  |

- 正则识别多级条款号（`3.1.2`）、中文章节标题（第X章）、表格边界，按条款/章节/表格切片；

- **块大小约 1400 字符（≈1k token）**：引用粒度与嵌入质量的折中——太短语义不完整，太长向量表征被稀释、引用定位变粗；同时对齐 vLLM 服务 4096 token 窗口留足余量；

- **重叠 180 字符只存在于兜底滑窗**：主路径的切块边界是条款边界，即语义断点，无需 overlap 弥补；只有超长条款按句末标点硬切时保留重叠，避免跨句信息断裂；

### 超长条款的三级处理机制

条款超过单块上限时不会"一刀两断丢上下文"，而是三级递进：

| 层级      | 触发条件               | 处理方式                            | 条款号                               |
| ------- | ------------------ | ------------------------------- | --------------------------------- |
| L1 完整保留 | 条款 ≤ 1400 字符       | 整条一个 chunk                      | `8.4.5`                           |
| L2 按句切分 | 条款 > 1400 字符       | 按。！？；句末标点切句累加，块间保留 **180 字符重叠** | 首块 `8.4.5`，续块 `8.4.5#2`、`8.4.5#3` |
| L3 单句硬切 | 单句本身 > 1400（无标点长句） | 800 字符窗口、650 步长（150 字符重叠）       | 同 L2 规则                           |

续块的关键设计：

- **元数据与首块完全一致**：chapter\_path、页码、source\_type 都复制首块，检索命中任一块都能正确溯源；

- **层级不断裂**：父级解析前先剥掉 `#n` 后缀（`8.4.5#2` → `8.4.5` → 父级 `8.4`），续块和首块是**同父兄弟**关系，不会产生"续块挂在首块下面"的错误层级；

- **检索侧无损**：`exact_clause_search` 用 `clause_no = ? OR text LIKE ?`，查 `8.4.5` 时首块等值精确命中排最前，续块靠正文 LIKE 与 BM25 通道召回。

### 真实 chunk 元数据示例

以《建筑防火通用规范》8.4.5 条为例（实际入库数据）：该条引用了大量其他规范条款，正文超过 1400 字符，触发 L2 按句切分，生成两个 chunk：

```json
// 首块（ordinal 0）
{
  "id": "ccefe31c-d3e7-46b7-888d-1278caff6907",
  "chapter_path": "",
  "clause_no": "8.4.5",              // 干净条款号，精确检索锚点
  "page_start": 6, "page_end": 7,    // PDF 物理页，引用跳转依据
  "source_type": "normative",         // 规范正文（优先于条文说明）
  "text": "8.4.5(1)、8.7.2(1、2)、8.10.1、8.10.4(1、2、3)..."
}

// 续块（ordinal 1）——同条款的第二段
{
  "id": "fab96407-4d0d-4f54-b974-f0148a637a8c",
  "chapter_path": "",                 // 与首块一致
  "clause_no": "8.4.5#2",            // #2 标记续块
  "page_start": 6, "page_end": 7,     // 与首块一致，溯源不受影响
  "source_type": "normative",
  "text": "B50383-2016第3.1.1、3.1.2(2、4、5)、4.2.3(1)...（共1228字符）"
}
```

表格 chunk 则是另一种形态（无条款号、携带结构化行文本）：

```json
{
  "chapter_path": "10 电 气",
  "clause_no": null,
  "source_type": "normative_table",
  "page_start": 2,
  "text": "表格行：建筑类别：建筑高度大于100m的民用建筑；连续供电时间(h)：1.5"
}
```

每个 chunk 携带 `clause_no`、`chapter_path`、页码、`source_type`（正文/条文说明/表格）、`parent_id` 父子层级等元数据——这些字段让引用卡片能跳转 PDF 原页、回答能区分证据等级、Wiki 概念页能按 chunk ID 回链原文。

一个容易被忽略的细节：**向量化输入是** **`chapter_path + clause_no + text`** **拼接**，让向量自带结构上下文——跨章节同名概念靠章节路径区分。

### 规范正文与条文说明怎么区分？

`source_type` 的判定不靠模型，靠国标"说明附于文末"的排版惯例——一个**单向分区状态机**按 block 顺序扫描全文：

```text
front_matter（前置页） → normative（正文区） → commentary（条文说明区）
```

触发切换的判定：

```python
if "条文说明" in text and len(text) <= 20:
    document_zone = "commentary"
```

- **单向状态机**：GB 规范结构固定——正文在前，"条文说明"作为独立部分整体附在文档末尾。见到标记块后一刀切，后续全部归说明区，不需要切回（国标不存在说明区后又有正文的情况）；

- **`len <= 20`** **是防误触发护栏**：正文或前言里"本规范条文说明由 XX 单位负责解释"这类句子都超过 20 字符，不会触发；只有独立标题块（4\~15 字符）命中；

- **切换前先** **`flush()`**：收完正文区最后一个未落盘 chunk 再切换，正文尾巴不会误入说明区；

- **表格/图片继承分区**：说明区内的表格标记为 `commentary_table`，与正文表格区分。

`source_type` 的下游消费（正文采信度恒高于条文说明）：

| 消费点    | 行为                                                         |
| ------ | ---------------------------------------------------------- |
| 精确检索排序 | `exact_clause_search` 排序：normative → normative\_table → 其他 |
| 回答生成   | 确定性结论只采信 normative，commentary 作为解释性证据补充                    |
| 检索加权   | 融合/重排阶段正文条款优先级高于条文说明                                       |

## Q3 Embedding：为什么选 Qwen3-Embedding-0.6B，而不是 BGE-M3？

**A**：

| 模型                           | 参数量   | 维度                 | 指令感知 | 显存（bf16） | 结论                                |
| ---------------------------- | ----- | ------------------ | ---- | -------- | --------------------------------- |
| **Qwen3-Embedding-0.6B（采用）** | 0.6B  | 1024（MRL 32\~1024） | 是    | \~1.2GB  | C-MTEB 中文领先、显存友好、同家族 Reranker 可搭配 |
| BGE-M3                       | 0.57B | 1024               | 否    | \~2.2GB  | 多功能但超出本项目需要                       |
| bge-large-zh-v1.5            | 0.3B  | 1024               | 否    | \~1GB    | 无指令感知，多任务场景弱                      |
| 商业 API（Jina 等）               | -     | -                  | -    | 0        | 依赖外网配额，与本地部署目标冲突，仅作 fallback      |

BGE-M3 的核心卖点是 dense + sparse + multi-vector 三路输出与 8K 长上下文；但 sparse 检索在本系统由 BM25 承担、multi-vector（ColBERT 式）在万级 chunk 规模收益不抵复杂度、chunk 已控制在 1k token 无需 8K 窗口——纯比 dense 中文效果与部署成本，Qwen3-Embedding 更优。

Qwen3-Embedding 是**指令感知非对称模型**：query 侧按官方要求加 Instruct 前缀（`Instruct: Given a web search query, retrieve relevant passages that answer the query`），document 侧不加。这是与传统对称模型的使用差异，不加前缀检索精度明显下降。

配套决策：Embedding 与 Reranker 选同家族（Qwen3），vLLM 同镜像部署，运维心智统一。

## Q4 向量库：为什么是 Qdrant？Milvus 的分布式能力不需要吗？

**A**：需要评估的是「规模匹配」而非「能力上限」。Milvus 的分布式能力（水平扩展、存算分离、亿级向量）是真实优势，但单机部署也要拖 etcd + MinIO 依赖组件。本项目规模：2170 chunks、向量数据约 10MB——Qdrant 单容器 + HNSW 完全覆盖。

| 项          | Qdrant（采用） | Milvus         | FAISS |
| ---------- | ---------- | -------------- | ----- |
| 部署         | 单容器        | etcd+MinIO+多组件 | 进程内库  |
| 持久化管理      | 原生         | 原生             | 需自管   |
| payload 过滤 | 原生         | 原生             | 无     |
| 分布式        | 弱          | 强              | 无     |
| 适配规模       | 万\~百万级     | 亿级             | 内存上限  |

两个工程细节：集合按模型版本命名隔离（`document_chunks_qwen3_embedding_v1`），换模型直接换集合，避免新旧量纲向量混存导致检索错乱；point id 复用 chunk UUID，与 SQLite、FTS5 以 chunk\_id 三方关联。

规模化路径：Qdrant 自身支持分布式模式；且向量库在架构上是 HTTP 调用隔离的，迁移成本收敛在 `vector_index.py` 单模块——不为假设性规模提前买单，但保留清晰升级路径。

## Q5 检索优化：为什么混合检索？重排到底起了什么作用？

**A**：规范提问存在两类形态，单路检索必丢其一：

- 「4.1.4 的耐火极限是 0.25h 吗」——带精确标识，**词法检索碾压语义检索**；

- 「新旧规范对厂房防火间距要求的差异」——自然语言问法，**必须语义召回**。

因此采用四段漏斗：

```text
查询理解（clause/comparison/summary/fact 分类 + 条款号精确通道）
  → BM25 + 向量双路召回（各 top 20）
  → RRF 融合（k=60，top 20）
  → Qwen3-Reranker 交叉编码精排（top 8）
```

**为什么 RRF 而非加权求和**：RRF 是融合多路召回结果的核心算法，全称是 Reciprocal Rank Fusion（倒数排名融合）。BM25 分数无界、余弦相似度 0\~1，量纲不同，直接加权需调权重且不稳定；RRF 只看排名、免疫分值尺度，且两路均命中的 chunk 分数叠加——天然奖励「词法+语义双确认」的证据，这正是理想条款证据的特征。

**重排的作用**：召回阶段的 embedding 是双塔结构（query/doc 独立编码），快但交互浅；Reranker 是交叉编码（query-doc 拼接联合编码），能判断「该条款是否真的回答了这个问题」，对「问 A 条但召回了相邻 B 条」的边界样本矫正明显。工程实现上通过 vLLM `--hf-overrides` 将生成式权重加载为 sequence classification，从 yes/no token logits 取 softmax，**单次前向直接出分（100\~300ms）**，无需生成文本再解析。

**漏斗数字 20/20 → 20 → 8 的逻辑**：融合后保留 20 给重排足够的候选区分度；最终 8 条是 LLM 上下文预算与证据噪声的平衡——证据太少回答片面，太多稀释注意力且引用稀疏。重排是检索链路最贵一环，只在融合后调用一次。

重排链路三级容灾：vLLM 主服务 → 云端 API（bge-reranker-v2-m3，硅基流动）→ 本地词项重合度排序，任一层失效不阻断问答。

对比类问题在此之上叠加 Agentic 编排：Planner LLM 参考文档目录与 Wiki 概念元数据拆解多维检索计划，并行执行、受控补检，并支持 `search_wiki` 按概念取关联 chunk 集合。

## Q6 LLM 生成：怎么保证回答可信？

**A**：按防线从外到内分层——提示词约束、证据结构约束、解码参数约束、生成后校验，最后是兜底降级：

### 第一层：提示词约束（ANSWER\_SYSTEM\_PROMPT）

回答模型的系统提示词是一份完整的"幻觉防火墙"（`prompt.py`），核心规则：

| 约束类别     | 提示词规则                                                             |
| -------- | ----------------------------------------------------------------- |
| **封闭世界** | "只能依据给定资料回答，禁止使用未提供的常识补充"——直接切断模型参数知识这个最大幻觉源                      |
| **强制溯源** | "每个关键结论后用实际资料编号标注 \[1]、\[2]"——无引用的断言在格式上不被接受                      |
| **编号校验** | "资料共几条就只能使用 \[1] 到该数字，不要把条款号或其他数字当作引用编号"——防止模型把 4.1.4 这类条款号误当引用标号 |
| **数值严谨** | "数值、单位、否定词和适用条件必须严格核对"——规范问答里 0.25h 写成 0.5h 是事故级错误                |
| **表格过滤** | "资料是表格、长列表或整段条款时，先筛选最相关的行列单元格，不要整表复述"——防止上下文噪声诱发串行幻觉              |
| **关系克制** | "资料中未体现的效力、废止关系不要编造"——新旧规范对比问题的幻觉高发区                              |
| **图片脱敏** | 模型不说"无法展示图片"，改为"参考资料预览中的图示"——防止模型描述不存在的图                          |

Planner 与 Wiki 生成各有独立的治理提示词（`PLANNER_SYSTEM_PROMPT` / `WIKI_GOVERNANCE_PROMPT`）：Planner 禁止编造文档目录之外的引用、只输出结构化 JSON；Wiki 侧明确"`storage/parsed` 的 chunk 是唯一原文事实来源，没有来源支持的内容不写入 Wiki"——派生知识层本身也被约束为不可引入新事实。

### 第二层：证据结构约束

证据不是一段拼接文本，而是带定位结构的 JSON（`evidence_payload`），每条资料自带 `standard_no`（标准号）、`version`（版本）、`clause_no`（条款号）、`pdf_page`（页码）、`type`（规范正文/条文说明）字段——模型要"编造"一条不存在的规范，需要同时伪造一整套互相一致的结构化定位信息，难度远高于自由文本续写。对比类问题的证据还按文档分组（`cross_document_comparison` 模式），进一步降低跨文档串扰。

同时 `evidence_text_for_llm()` 会把内部图片文件路径替换为占位符——防止模型把存储路径当答案输出（真实踩过的坑）。

### 第三层：解码参数约束

`temperature: 0.1`——生成侧刻意牺牲多样性换取确定性。规范问答不存在"发挥空间"，事实性任务用低温是共识；配合 `max_tokens` 上限防止失控长文本。

### 第四层：生成后校验（引用对齐）

回答完成后 `_used_citations` 过滤：引用列表只保留正文实际标注 `[n]` 的资料——模型若引用了检索列表之外的编号，该引用直接不展示（宁可少一条引用，不展示一条对不上的）。

### 第五层：兜底降级

LLM 服务完全不可用时，系统退化为返回原文证据清单（`_extractive_answer`）——用户拿到的是未经生成的原始条款，零幻觉但也零综合。这是明确的取舍：**可用性优先于智能化程度**。

### 为什么"提示词不是唯一防线"

提示词是软约束——模型可能遵守也可能不遵守，所以这套设计的思路是让每一层都独立可失效：提示词失效时引用校验拦住、证据 JSON 结构让编造成本变高、低温解码压缩发挥空间、极端情况退出生成。**可信性来自约束的冗余，不来自任何单点。**

## Q7 整体：贯穿全链路的设计原则是什么？

**A**：三个词：

- **可降级**：每层有 fallback——解析五管线、检索 BM25 兜底、重排三级链路、生成回退原文证据；

- **只算一次**：解析落盘复用（`normalized.json`）、模型常驻容器 + 缓存卷，请求路径上只有推理；

- **规模匹配**：万级 chunk 用 Qdrant/SQLite 而非 Milvus/ES，0.6B 模型 + 各 20% 显存预算——不为假设性规模买单，但保留清晰升级路径。

## 运维思考

| 维度  | 考量                                                                          |
| --- | --------------------------------------------------------------------------- |
| 时延  | FTS5 <10ms + embedding 20~~50ms + rerank 100~~300ms；rerank 是检索链路最贵一环，只调用一次  |
| 高并发 | vLLM continuous batching 消化并发，多路并发时延亚线性增长；解析走串行队列（`RAG_MAX_WORKERS=1`）防内存打爆 |
| 显存  | Embedding/Reranker 两容器各锁 20% 预算（合计约 2.4\~3.2GB），与解析服务共卡不冲突；调大前先确认同卡峰值       |
| 观测  | retrieval\_ms / first\_token\_ms / total\_ms 写入 metrics 日志，可定位慢在召回还是重排      |
| 可移植 | 镜像 + 模型缓存卷 + `storage/` 三件套整体迁移到任何装 Docker 的机器；GPU profile 缺失时降级运行          |
